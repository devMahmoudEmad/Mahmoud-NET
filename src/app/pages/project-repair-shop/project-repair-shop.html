Engineering Case Study

Repair Shop Management System

Cross-platform desktop application managing the complete lifecycle of a mobile repair shop

Solo Developer · C# · Avalonia UI · MVVM · SQLite

Overview

The Repair Shop Management System is a cross-platform desktop application I independently designed, developed, and deployed for managing mobile repair shop operations. The application handles the full business workflow — device intake, diagnostics tracking, repair workflow, inventory management, invoicing, daily financial reports, and delivery confirmation. Built with Avalonia UI following the MVVM pattern, and using Dapper with SQLite for lightweight, high-performance data access.

Business Problem

Small mobile repair shops typically rely on paper records, spreadsheets, or generic POS systems that do not capture repair-specific workflows. Common problems include lost repair tickets, incorrect pricing, untracked inventory, and difficulty generating daily financial reports. The goal was to build a purpose-built application that digitizes the entire repair lifecycle — from device drop-off to collection — while remaining simple enough for shop employees to adopt without training.

MVVM Pattern: ViewModels expose observable properties and commands that the XAML views bind to. This keeps UI code declarative and business logic testable without UI dependencies.
Dapper over EF Core: Chosen for desktop use — minimal overhead, full SQL control, and faster startup time compared to EF Core. The trade-off is more manual SQL, which is acceptable for a focused application with well-defined queries.
SQLite: Embedded database eliminates server dependencies. The app runs standalone on any machine with zero configuration, making deployment trivial for small shop owners.

Engineering Decisions

Why Avalonia UI?
Avalonia was chosen over WPF because it supports Windows, Linux, and macOS from a single codebase. The XAML-based UI framework is familiar to .NET desktop developers, and its styling system allows for a modern, clean interface without the legacy baggage of Windows Forms.
Why MVVM?
MVVM provides clean separation between UI (XAML views) and business logic (ViewModels). ViewModels are testable without instantiating windows or controls. The pattern also makes it straightforward to swap the UI layer without changing business logic.
Why Dapper instead of EF Core?
For a desktop application with focused, well-understood queries, Dapper's minimal overhead and full SQL control are advantages. EF Core's change tracking and migration pipeline add complexity that provides little value for a local SQLite database with simple CRUD operations.
Why SQLite?
SQLite eliminates deployment complexity. The database is a single file that travels with the application. No server installation, no connection strings to configure, no service dependencies. For a single-user or small-team desktop application, this is the correct trade-off.

Lessons Learned

Solo Ownership

Building an application from scratch without a team teaches end-to-end ownership — requirements analysis, architecture, implementation, testing, deployment, and user feedback iteration. Every decision is both an opportunity and a responsibility.

Desktop UI Design

Desktop UI development requires a different mindset than web. State management is local, threading matters for responsiveness, and the user expects native-feeling interactions. Avalonia's XAML system made this manageable.

Pragmatic Data Access

Choosing Dapper over EF Core for a desktop app was the right call. The simplicity of raw SQL with Dapper's thin wrapper kept the data access layer transparent and performant without the overhead of an ORM.
